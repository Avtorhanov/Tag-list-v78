# Tag list v77 — UI/UX, logic, reliability and performance audit

## Scope

Исходник: Tag-list-v76-main. Аудит проведён по HTML/CSS/JS, service worker, PWA manifest и текущей структуре модулей.

## Что было найдено

1. **Статус и выбор тегов были смешаны в одном управляющем действии.**
   В режиме выборки `Отметить все` фактически означало `Выбрать все`. Поэтому отдельного действия для массового выполнения уже выбранных тегов не было.

2. **Повторный запуск мог зависеть от сети.**
   В service worker навигация использовала network-first: сначала выполнялся сетевой запрос, а кэш был fallback. Для уже установленного PWA это не оптимально для быстрого повторного запуска.

3. **APP_SHELL содержал дублирующиеся ресурсы.**
   `manifest.webmanifest`, `css/app.css` и `js/app.js` повторялись в списке precache.

4. **Зачёркивание было мгновенным.**
   Сам статус менялся без задержки, но визуальная линия не имела отдельной плавной анимации.

5. **Тактильная обратная связь отсутствовала непосредственно при смене статуса.**
   В проекте уже использовался `navigator.vibrate()` для долгого выбора, поэтому тот же безопасный механизм добавлен к изменению статуса. Если браузер/устройство не поддерживает Vibration API, действие не ломается.

6. **Для длинных списков весь DOM списка создавался заново при ряде операций.**
   Существующий `DocumentFragment` уже был правильным решением; дополнительно добавлена поддержка `content-visibility:auto` для строк там, где браузер её поддерживает.

## Что изменено

### UX

- Добавлен лёгкий splash-screen с иконкой Tag list при открытии.
- Splash использует уже существующую иконку, без дополнительного сетевого ресурса.
- Добавлена плавная анимация зачёркивания через анимируемый `text-decoration-color`.
- Добавлена тактильная обратная связь при изменении статуса через `navigator.vibrate(18)`.
- В режиме выборки добавлена отдельная кнопка `Выполнить выбранные`.
- Существующие `Выбрать все`, `Снять выбор` и `Удалить выбранные` не переопределены и сохраняют исходную логику.
- Состояние выбранных тегов не используется как состояние `done`: это две независимые сущности.

### Передача состояния

Добавлен пункт `Ссылка с состоянием`.

В ссылку входят:
- все страницы;
- порядок страниц;
- название документа;
- теги;
- `unit`;
- статус `done`;
- задания;
- активная страница;
- тема;
- размер шрифта;
- выбранное семейство шрифта.

Состояние хранится во fragment URL (`#state=...`), поэтому оно не отправляется серверу как часть HTTP-запроса.

При открытии такой ссылки приложение валидирует данные и восстанавливает их в локальное хранилище текущей версии.

Ограничение: размер URL ограничен браузером/мессенджером. Для обычных инженерных перечней это подходит, но для очень больших списков ссылка может стать слишком длинной. Это архитектурное ограничение URL, а не ошибка сохранения данных.

### Производительность

Service worker переведён для оболочки приложения на cache-first с обновлением navigation в фоне:
- повторный запуск получает уже закэшированную оболочку;
- сеть не блокирует повторный запуск;
- при наличии сети новая версия обновляет кэш;
- при отсутствии сети приложение использует кэш.

Это соответствует стандартным стратегиям cache-first / stale-while-revalidate, описанным MDN.

## Ограничение тактильной вибрации

`Navigator.vibrate()` относится к Vibration API и имеет ограниченную совместимость. Поэтому реализация сделана capability-safe: при наличии API вызывается короткий импульс, при отсутствии приложение продолжает работать без исключения.

Источник: MDN — Vibration API:
https://developer.mozilla.org/en-US/docs/Web/API/Vibration_API

## Service Worker

Источник: MDN — Progressive Web Apps / Caching:
https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Caching

MDN описывает cache-first и cache-first-with-refresh как стратегии, позволяющие быстро отдавать кэшированный интерфейс и обновлять кэш сетью в фоне.

- OCR-поток;
- импорт файлов;
- редактирование/удаление тегов;
- страницы и их управление;
- фильтры `Все / Задания / Выполненные / Невыполненные / Unit`;
- копирование;
- экспорт;
- PWA manifest;
- существующая визуальная система и основные размеры элементов.

Цель изменений — добавить требуемые функции и повысить устойчивость/скорость без перестройки бизнес-логики проекта.
